## Findings

**Yes, Go runs in the browser, and it's fast enough to be irrelevant.**
Measured on the spike:

| Metric | Value |
|---|---|
| `sim.wasm` raw / gzip | 3351 KB / **934 KB** |
| with `-ldflags="-s -w"` | 3285 KB / 914 KB (barely helps) |
| `wasm_exec.js` glue | 16 KB / 4 KB |
| 800-event run, warm | **1.8 ms** |
| Determinism across instantiations | byte-identical |

~2 MB of that binary is Go's runtime + GC — a floor you pay regardless of how
small the code is. Stripping symbols saves ~2%, so don't bother. Real lever is
lazy-loading (homepage needs zero wasm) or TinyGo later.

**WASM ships the program, not its output.** Worth writing down because I had
this backwards at first: the `.wasm` file is a compiled executable the visitor
downloads and runs *in their tab*. Nothing is precomputed. A user dragging
"nodes: 4 → 6" causes the Go engine to execute right then with those
parameters. This is a completely separate mechanism from replaying a recorded
JSON event log, which *is* pre-baked. Both are useful; they are not the same
thing.

**The browser has no filesystem, and it lies about it.** Read the fs stub in
`$(go env GOROOT)/lib/wasm/wasm_exec.js`:

```js
open(path, flags, mode, callback) { callback(enosys()); },   // os.Create fails
fsync(fd, callback) { callback(null); },                     // SUCCEEDS, does nothing
```

`open` returns `ENOSYS`, so there is no filesystem at all by default. But
`fsync` silently reports success while doing nothing — **a WAL built on this
would pass every test and guarantee nothing.** This is the single most
dangerous fact for the LSM work. There is an escape hatch (the stub is guarded
by `if (!globalThis.fs)`, so you can supply your own ~25-function
implementation over OPFS), but it does not rescue the learning objective: the
LSM's definition of done is "kill -9 mid-write, restart, read every
acknowledged key back," and you cannot faithfully kill -9 a browser tab.

**WASM is single-threaded.** Verified: native `GOMAXPROCS=10 NumCPU=10`, wasm
`GOMAXPROCS=1 NumCPU=1`. Goroutines are cooperatively scheduled, never
parallel. For a deterministic simulation this is a *feature* — no scheduler
nondeterminism, so same seed genuinely means same bytes. But real data races
and true parallelism cannot be demonstrated in the browser; they must stay
native or be modelled rather than actually raced.

**The dividing line, stated once so it doesn't need re-deriving:**
*WebAssembly gives you the algorithm, not the environment.* Learning an
algorithm (quorum arithmetic, Raft election rules, consistent hashing, vector
clocks, compaction strategy) → runs in the browser, interactively. Learning a
systems property (fsync surviving power loss, TCP reordering, a process dying
mid-write, real cores racing) → stays native. Every visualization on the list
is algorithm-side. Every "real system" build is environment-side.

**Raft splits cleanly and the split improves the Go.** If Raft is written as a
pure state machine — `Step(msg) → (newState, []outbound)` with transport and
storage injected — the same code runs natively over TCP *and* in-browser over
a simulated network. That's how etcd's raft library is built anyway. Same
trick applies to Gossip Glomers: Maelstrom is a JVM harness spawning
subprocesses (never browser-portable), but its wire format is `{src, dest,
body}`, near-identical to a sim message. Handlers written against a small
interface rather than `maelstrom.Node` directly could run in both. Cheap to
decide at challenge #1, expensive to retrofit across six.

## What I got wrong / missed

- **The original scaffold committed to a three-layer architecture (engine →
  concepts → renderers) before a single visualization existed.** Folders,
  interfaces, and a cross-language contract were all designed against zero
  real use cases. Classic premature abstraction. The new plan corrects this
  directly: no shared engine until November, extract it from three working
  standalone visualizations. Duplication first, abstraction second.
- **`logs/schema.md` was a contract between two things that didn't exist yet**,
  and it required manual mirroring across three files (TS types, Go structs,
  markdown). Deleted. When event logs come back, generate one side from the
  other.
- **I asked for build decisions when a feasibility answer was wanted.** Went
  straight to proposing folder restructures and a rendering-split question
  before establishing whether the thing was even possible. Answer the question
  asked, then stop.
- **A live GitHub PAT was sitting in plaintext** in `tmp/Abhijit25Mishra/.git/config`
  (embedded in the remote URL). Gitignored so it never got committed here, but
  it sat on disk for a month. Deleted with the folder — **token still needs
  rotating.**
