## Findings

**FNV-1a alone is unusable for virtual node ids, and the failure is silent.**
This was the session's real finding. FNV-1a's last operation is
`imul(h ^ lastChar, PRIME)`, so two strings sharing a prefix differ by a small
integer multiple of the prime. Virtual node ids are exactly that shape:

```
n1#0  1598427531
n1#1  1581649912   diff -16777619  = -1.00 x FNV prime
n1#2  1631982769   diff  50332857  = +3.00 x FNV prime
n1#3  1615205150   diff -16777619  = -1.00 x FNV prime
```

Ten replicas spanned **5.86%** of the ring where uniform would be ~82%. So all
150 replicas of a node sat in a few tight clumps, virtual nodes bought nothing,
and load skew did not fall as V rose:

| V | plain FNV-1a | FNV + fmix32 | theory 1/sqrt(V) |
|---|---|---|---|
| 1 | 0.5439 | 0.5185 | 1.0000 |
| 50 | 0.5640 | 0.0592 | 0.1414 |
| 200 | 0.1375 | 0.0460 | 0.0707 |
| 500 | 0.1450 | 0.0519 | 0.0447 |

Adding MurmurHash3's `fmix32` finalizer fixed it. After: ten replicas span
91.5% of the ring, and skew tracks theory.

**Keys were never the problem, which is why it hid.** Key bin CV measured
0.0164 against 0.0126 for uniform — fine. `hash` is only weak on short
prefix-sharing inputs, so the key-distribution test passed throughout. The
same function was good enough for `assignModN` (which reads low bits via `%`)
and bad for the ring (which reads high bits as position). One hash, two
different quality requirements.

**The measured headline, which is what the page exists to show:**

```
adding a 5th node to 4, over 100,000 keys
  consistent hashing moved: 19.5%     (theory 20.0%)
  hash % N moved:           80.0%
```

**Node positions do not depend on the seed, and that makes V=1 misleading.**
Caught while picking a default. At V=1 the churn figure reads ~2% for *every*
seed:

```
seeds      1     7    42    99   256   512   777
V=1      1.7   1.8   2.3   1.3   1.2   2.3   2.2
V=120   17.5  16.0  17.7  18.5  18.5  17.5  20.2
```

Not noise. Positions come from `hash("n5#0")`, a fixed value; the seed only
changes the keys. `n5` happens to land just behind its predecessor and inherits
a sliver, so the number is both wrong and stable, which is the worst
combination. The figure now opens at V=120, where the number is representative;
dragging down to 1 still shows the lumpiness.

**Labels collide at high V, and "widest arc" stops meaning anything.** At 150
virtual nodes every arc is a sliver, so the widest one is effectively arbitrary
and two labels landed on top of each other at 12 o'clock. Fixed with an angular
relaxation pass that preserves position when there is room. Needed, not
cosmetic: past three simultaneous series colour cannot carry identity on a
ring, so an unreadable label means an unidentifiable node.

## What I got wrong / missed

- **I shipped two tests that measured proxies instead of properties, and they
  hid a real defect for a whole session.** The avalanche test compared five
  strings, took the *median* gap, and required only `> 1%` of the ring — a
  clustering hash clears that trivially. The skew test allowed `< 0.2` at V=200
  where theory says 0.071, so 0.19 passed. 23/23 was green while the hash was
  broken. Both tests are mine. Rewritten to measure distribution over 2000
  replicas and to assert the *trend* between V=50 and V=500.
- **Same failure mode as `generateKeys` earlier in the week**: "is reproducible
  from the same seed" passed with 500 identical strings. A test a degenerate
  implementation satisfies is not a test. That is twice now; the habit to build
  is measuring the property directly rather than inferring it from a green
  assertion.
- **The toolchain was not catching unreachable code, and neither layer
  admitted it.** Dead `throw`s survived after `return` in three files.
  `typescript-eslint`'s recommended config disables `no-unreachable` on the
  assumption TypeScript reports it; `tsconfig.app.json` never set
  `allowUnreachableCode: false`, so TypeScript did not. Each deferred to the
  other. ESLint said 0 problems and tsc said no errors. Now set.
- **My label placement did not survive its own parameter range.** "Put the
  label on the node's widest arc" is right at V=1 and meaningless at V=150. I
  wrote it without considering the slider I was about to add.
- **My relaxation code had a bug my own test caught**: taking the modulo inside
  the loop let a pushed label cross its neighbour, invalidating the sorted
  order the sweep depends on, so it fixed the wrong pairs and never converged.
  Relaxing on an unwrapped line and handling the wrap once fixed it. Worth
  noting the test caught it before the screenshot did, which is the first time
  that has happened this week.
- **`fmix32` was written by the agent, crossing the hand-written boundary.**
  Asked for directly, after the diagnosis had been worked through together. The
  five lines are published constants and typing them teaches nothing, but the
  boundary in `CLAUDE.md` marks `hash.ts` as mine and this crossed it. Recorded
  in `lab/SKILLS.md` review #3 rather than left quiet. Had it been handed over
  before the diagnosis, it would have been a real loss.
- **Ch 2 was due today and did not move.** Two sessions went entirely to code.
